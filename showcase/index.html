seen‑before

Someone files an issue. Somewhere in the archive, earlier ones are waiting. Has anyone reported this before?

At an AI convention, trained-model and embedding pipelines were being pitched for exactly this: train a model on all the past tickets, and let it find the closest ones. The question we took home was simple. Is this the right way to do it?

So we built it, built the alternatives, and compared them on the same issues.

Scroll to watch the approaches answer the same issues.

Every dot on the right is a real issue from three open-source projects on GitHub: Microsoft PowerToys, Windows Terminal and WSL. This new one came in after all of them:

A maintainer later marked it as a duplicate of one earlier issue. Both approaches below get the same question, the same archive and the same AI model, Claude Sonnet 5.5. Each one has to name that earlier issue.

The trained model

First, a language model is trained on the archive, so that issues about the same problem end up close together. That took 17 minutes on a GPU. Every issue becomes a point in a map of meaning, and the dots on the right move to their places in it.

The new issue lands on the map. The five closest issues are handed to Claude, which reads them once and answers.

Here all five are about the clipboard or escape sequences, and none of them is the one. Claude says not seen before. The right issue is close by on the map, but not among the five.

The agent with ripgrep

Nothing is trained. The dots go back to plain order, one file per issue. Claude gets one tool that searches those files for exact text, and one that reads a file. It decides what to look for.

It starts with the words that only this bug would contain. Highlighted dots are the issues each search matches.

It reads , runs two more searches to check, and names it. Right, after turns.

It cuts both ways

Here the issue is a few plain words. On the map of meaning, two of its five neighbours are earlier requests for exactly this. Claude names one. Right.

The agent searches for translation. That matches issues, and it is shown the top 20. Two of those 20 are this same request. It passes over them, tries two narrower phrases that match nothing, and answers not seen before. Wrong.

In these two, words found a bug by its error message, and meaning found a wish by what it asks for.

Over issues

We ran the same thing on issues filed after the archive was cut. Each one has a known earlier report, marked by a maintainer. We also ran three mixes of the two approaches.

The agent with ripgrep named the right issue first more often than the trained model, narrowly. Agents with the trained model as their search tool did best of all, though not by enough to tell them apart from the ripgrep agent.

Side by side

Accuracy is one measure among several. The one-shot pipelines answer three times faster and cost less. The agents need more turns, and the ripgrep agent needs nothing trained, no GPU and no index.

How each one would be measured was written down before the first run. Where an approach loses, it says so here.

So, is it the right way?

On these issues, training a model was not the step that mattered. Letting the AI search more than once was: an agent that can look, read, and look again.

Give the trained model to an agent instead of a one-shot pipeline, and it goes from to . Swap that model for ripgrep and the agent gets , too close to call. Ripgrep simply needs no training, no GPU and no index to keep up to date.

The connector

So we shipped the simplest approach within reach of the best: the agent with ripgrep, as a GitHub Action and a Claude Code plugin. When an issue is opened, it looks through the past ones and comments if it finds an earlier report.

The comment is built only from issue numbers the tools really returned, and their stored titles. The agent's own words are never posted.

We named it seen‑before after the reflex an agent should reach for first: have I seen this before?
